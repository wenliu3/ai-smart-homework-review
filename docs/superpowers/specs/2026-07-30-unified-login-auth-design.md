# 统一账号登录与认证错误处理设计

## 背景

当前登录页要求用户先选择“用户名登录”“学号登录”或“邮箱登录”，再填写对应字段。但后端 `POST /api/v1/auth/login` 已经通过同一个 `usernameOrEmailOrStudentId` 字段，同时匹配 `users.username`、`users.email` 和 `users.student_id`，前端的登录方式选择没有提供额外能力。

浏览器测试还稳定复现了认证错误：用户退出登录后使用错误密码登录，后端正确返回 HTTP 401 和“账号或密码错误”，前端响应拦截器却把这个 401 当作访问令牌过期，调用 `user/refreshToken`。由于此时没有刷新令牌，页面最终显示“登录已过期，请重新登录”并弹出“认证失败”，掩盖了真正的登录错误。

## 目标

- 登录页仅展示“账号”“密码”两个主要输入项，账号可填写用户名、邮箱或学号。
- 保持现有后端统一登录接口和数据库结构不变。
- 登录、注册、找回密码等公开认证请求不携带旧访问令牌，也不参与访问令牌刷新。
- 错误账号或密码直接显示后端返回的“账号或密码错误”，不弹会话过期对话框。
- 仅受保护接口返回 401 时触发单飞刷新；刷新失败后完整清理用户、权限和持久化认证状态。
- 新账号登录成功时完整替换旧账号状态，避免不同角色的字段残留。

## 非目标

- 不改变 JWT、刷新令牌格式和有效期。
- 不修改用户表或增加数据库迁移。
- 不实现注册、找回密码或验证码的新业务能力。
- 不根据账号字符串格式在前端判断账号类型；识别仍由后端基于唯一字段查询完成。

## 方案

采用方案 A：统一登录输入，同时修正公开认证请求与会话刷新边界，并集中清理认证状态。

### 登录界面

登录模式下移除登录方式分段选择，以及独立的用户名、邮箱和学号输入框，改为单一字段：

- 标签：`账号`
- 占位文本：`请输入用户名、邮箱或学号`
- 表单属性：`account`
- 校验：去除首尾空白后不能为空，长度 1 至 255 个字符

密码、记住我、忘记密码和提交按钮维持现状。注册模式仍保留独立的用户名与邮箱字段。

提交登录时发送：

```ts
{
  usernameOrEmailOrStudentId: form.account.trim(),
  password: form.password,
  rememberMe: form.rememberMe,
}
```

后端继续用一条查询匹配用户名、邮箱或学号，因此用户名、邮箱和学号的行为一致，前端不显示或保存推断出的账号类型。

### 公开认证请求边界

在请求封装中定义集中判断函数，将下列路径识别为公开认证请求：

- `/v1/auth/login`
- `/v1/auth/register`
- `/v1/auth/forgot-password`
- `/v1/auth/reset-password`
- `/v1/auth/refresh-token`
- 兼容路径 `/auth/login` 和 `/auth/register`

请求拦截器不会给这些请求附加 `Authorization`。响应拦截器收到登录、注册、找回密码或重置密码的 401 时，直接提取后端 `message` 并拒绝请求，不触发刷新、不弹全局认证失败对话框。登录页负责在表单内展示该错误。

`/v1/auth/refresh-token` 的 401 仍表示刷新失败，但只负责结束当前刷新流程；外层受保护请求统一执行会话清理和登录跳转，避免同一个错误触发两次弹框。

### 受保护请求刷新流程

受保护接口返回 401 时沿用单飞刷新机制：

1. 第一个失败请求发起一次刷新，其他失败请求进入队列。
2. 刷新成功后用新访问令牌重放原请求并释放队列。
3. 刷新失败后拒绝队列，执行统一会话清理，再显示一次认证失败提示并跳转登录页。
4. 登录页上的公开认证失败永远不会进入此流程。

### 认证状态管理

用户 Vuex 模块增加两个明确动作：

- `replaceSession`：用新的登录结果完整替换 `state.userInfo` 和本地存储；登录成功使用该语义，不能与旧用户信息合并。
- `clearSession`：清空 `state.userInfo`、刷新中的 Promise、`localStorage.userInfo` 和 `localStorage.token`。

权限模块继续只负责菜单、角色和权限。完整退出或认证失败时依次执行 `user/clearSession` 与 `auth/clearPermissions`。这样内存状态和本地存储保持一致，刷新逻辑不会再读到旧账号的刷新令牌。

正常的用户资料更新与刷新令牌成功仍可合并当前会话字段，避免丢失角色和个人资料。

## 错误呈现

- 错误账号或密码：登录表单内显示 `账号或密码错误`，不弹认证过期对话框。
- 被禁用或锁定账号：显示后端原始业务消息，不尝试刷新。
- 访问令牌过期且刷新成功：用户无感知，原请求自动重放。
- 刷新令牌无效或过期：只显示一次认证失效提示，清理完整会话后跳转登录页。
- 网络错误或服务器错误：沿用通用请求错误处理，不伪装成认证过期。

## 测试设计

### 前端单元测试

- 登录页只渲染一个账号输入框，不渲染登录方式选择。
- 用户名、邮箱和学号字符串均原样填入 `usernameOrEmailOrStudentId`，首尾空白被移除。
- 登录接口返回 401 时不调用刷新动作，错误消息保持为“账号或密码错误”。
- 受保护接口返回 401 时只发起一次刷新，并在成功后重放请求。
- 刷新失败时清理用户状态、权限状态和本地存储。
- 新账号登录成功后不保留旧账号特有字段。

### 后端回归测试

- 同一登录接口分别使用用户名、邮箱和学号均可定位同一用户。
- 不存在的账号和错误密码均返回统一的认证错误。

### 浏览器验收

- 登录页仅显示“账号”和“密码”。
- `teacher` 可通过用户名登录。
- 有效教师邮箱可通过邮箱登录。
- `2024041` 可通过学号登录并进入学生工作台。
- 错误密码只显示“账号或密码错误”，页面不出现“登录已过期”或认证失败对话框。
- 教师退出后登录学生、学生退出后登录教师，角色、姓名和菜单均正确切换。

## 兼容性与风险

- API 请求字段不变，后端与已有客户端保持兼容。
- 登录页表单字段属于前端内部状态，不影响数据库或接口契约。
- 最大风险在响应拦截器分支顺序；通过公开认证 401、受保护接口 401 和刷新失败三组测试隔离验证。
- `rememberMe` 当前仍由既有接口接收，刷新令牌签发策略不在本次范围内。

## 验收标准

- 用户不需要选择账号类型即可使用用户名、邮箱或学号登录。
- 登录失败消息准确，不触发 Token 刷新或会话过期弹框。
- 受保护接口的 Token 自动刷新能力不回退。
- 切换角色登录后不存在旧用户内存状态残留。
- 前端单元测试、类型检查、后端认证测试以及三种账号浏览器回归全部通过。
