# 可选独立结构化模型批改链路设计

## 背景

学生正式提交作业后，系统当前使用教师在作业中保存的 `aiRule` 快照构造双 Agent 批改任务。`aiRule.modelType` 表示教师选择的批改模型，`aiRule.prompt` 表示教师定义的评分规则。现有实现把多模态批改模型直接包装为 `response_format=GradingDraft` 的 LangChain Agent；当模型不支持结构化工具调用或输出不符合 Schema 时，LangChain 内部 `model -> model` 循环会重复发送整份正文和图片，最终触发 Celery 超时，并可能使 `AgentRun` 永久停留在 `processing`。

管理员需要能够决定是否接入一个独立的结构化输出模型：

- 关闭时，沿用“AI 规则模型直接结构化”的链路；结构化失败属于 AI 规则与所选模型不兼容，不切换其他模型。
- 开启时，AI 规则模型只负责按教师规则生成普通文本批改报告；管理员指定的模型把两份报告整理成后端 Schema。
- 无论开关状态如何，任务都必须有限调用并进入确定的终态，不能无限请求或永久显示“批改中”。

## 设计原则

1. 教师控制评分语义：`aiRule.modelType` 和 `aiRule.prompt` 是批改依据，不由管理员结构化模型改写。
2. 管理员控制系统集成：是否使用独立结构化模型、使用哪个模型及其 API 配置由超级管理员维护。
3. 结构化不等于重新评分：独立结构化模型只能整理主批改和复核报告，缺失事实时必须返回失败，不能补造分数或证据。
4. 双路径行为显式：开关关闭和开启分别有独立测试，禁止隐式回退到默认模型。
5. 失败必须收口：模型不兼容、解析失败、软/硬超时都必须更新 Run 和提交状态，并给前端持久反馈。

## 配置模型

复用现有 `ai_models` 表，不新增模型凭据表。现有字段已经覆盖 `code`、`model_name`、`base_url`、`api_key`、`status`、`capabilities` 和 `profile_bindings`。

独立结构化模型是否启用由绑定是否存在表示：

```json
{
  "capabilities": ["text", "structured_output"],
  "profileBindings": {
    "grading_structurer": true
  }
}
```

约束：

- 全库最多一个模型可绑定 `grading_structurer=true`。
- 没有绑定即表示关闭独立结构化模型。
- 绑定目标必须是 `active` 且具有非空 API Key 的模型。
- 关闭开关时清除所有模型的 `grading_structurer` 绑定，不删除模型或密钥。
- API 响应继续只返回掩码密钥。

管理员端提供全局卡片：启用开关、结构化模型下拉框、当前模型信息、连接测试和结构化能力测试。模型名称、Base URL、API Key 仍使用已有模型编辑表单维护。

## 双路径数据流

### 路径 A：独立结构化模型关闭

```text
提交内容 + 教师 AI 规则
  -> AI 规则指定模型（主批改，直接 GradingDraft）
  -> AI 规则指定模型（独立复核，直接 GradingDraft）
  -> 确定性比较
  -> 写回或转人工
```

要求：

- 必须根据 `aiRule.modelType` 精确选择 `AiModel.code`，不得回退系统默认模型。
- 保留现有结构化 Agent 语义，但每个 Agent 的 LangGraph `recursion_limit` 固定为 2，只允许首次生成和一次内部修复。
- 任一 Agent 仍无法产生合法 `GradingDraft` 时，Run 进入受控失败/转人工，不尝试管理员结构化模型。

### 路径 B：独立结构化模型开启

```text
提交内容 + 教师 AI 规则
  -> AI 规则指定模型（主批改，普通文本）
  -> AI 规则指定模型（独立复核，普通文本）
  -> 管理员结构化模型（一次调用，整理两份报告）
  -> GradingReportPair
  -> 确定性比较
  -> 写回或转人工
```

要求：

- 两个批改 Agent 均能看到完整正文和图片，并独立执行同一份教师规则。
- 普通文本 Agent 不绑定工具、不传 `response_format`，因此每个 Agent 正常只产生一次模型请求。
- 结构化模型只收到教师规则、版本化量表和两份普通文本报告；不接收原始附件或图片，避免它成为第二评分者。
- 结构化模型一次返回主批改与复核两份草案，减少额外调用。
- 结构化结果仍通过现有 `validate_against()` 校验维度 ID、满分、量表版本和分数边界。
- 缺少可提取的分数或证据时，结构化结果必须声明失败；后端不得凭空补值。

## 规则快照与模型路由

作业继续保存 AI 规则快照，避免规则后续修改影响已经发布的作业。快照补齐 `maxScore`，形成：

```ts
interface AiRuleSnapshot {
  id: string;
  name: string;
  modelType: string;
  prompt: string;
  maxScore: number;
}
```

旧快照缺少 `maxScore` 时兼容为 100。批改任务调度前检查：

- `modelType` 对应的模型存在；
- 模型处于 active；
- API Key 已配置；
- 规则 prompt 非空。

不满足时不调用其他模型，而是记录稳定错误码并提示教师修正规则或管理员模型配置。

## 运行状态与超时

模型调用预算必须覆盖真实 HTTP 请求，而不只统计外层 `agent.invoke()`：

- 直接路径：每个批改 Agent 最多 2 次底层请求。
- 独立结构化路径：两个普通文本批改请求 + 一个结构化请求；结构化请求最多一次内部修复。
- 主批改与独立复核的单次底层模型请求超时为 35 秒，结构化模型单次请求超时为 20 秒。
- Celery 批改任务使用 120 秒软超时、150 秒硬超时；结构化路径最坏的四次请求预算为 110 秒，另留 10 秒完成解析和落库。

当前 Celery 5.6 的硬超时会在父进程杀死子进程，子进程 `except` 无法完成 Run 收口。因此增加批改任务专用 `Request.on_timeout()`：硬超时时使用任务 kwargs 中的 `run_id`、`user_id` 将活动 Run 标记为 `failed/AGENT_GRADING_TIMEOUT`。

再增加读取时的陈旧 Run 防线：`processing` 批改 Run 自 `started_at` 起超过 180 秒仍无终态时，状态查询将其收口为超时失败。该逻辑只处理 `intent=grading` 且 `status=processing` 的运行。

## 产物与用量

两条路径都保留可审计产物：

- `grading_outcome`：最终结构化结果。
- `grading_raw_reports`：独立结构化路径下的主报告和复核报告。
- `grading_raw_draft`：结构化或校验失败时的有限原始信息。

模型用量按实际模型分别累计：AI 规则模型记录两次批改调用，结构化模型记录结构化调用；禁止继续把全部用量记到默认模型。

## 前端行为

学生端不再仅凭“没有分数”显示评价中：

- `running/processing`：显示评价进行中和刷新次数。
- `completed + aiReview`：显示 AI 结果。
- `failed`：持久显示错误说明和“等待教师人工批改”。
- `cancelled`：显示任务已取消。
- 超过轮询上限只停止请求，不再宣称 AI 仍在处理。

管理员端保存绑定前可以执行结构化能力测试。测试使用最小固定 Schema，不读取学生数据；失败时禁止启用绑定。

## 安全与权限

- 配置、绑定和能力测试端点仅 `superadmin` 可用。
- API Key 永不返回明文；客户端回传掩码或空值时不覆盖数据库密钥。
- 教师和学生只能看到运行状态与业务错误码，不能看到模型密钥或原始结构化调试内容。
- 结构化模型输入中的普通报告按不可信内容包裹，防止报告中的指令改变 Schema 或系统规则。

## 成功标准

1. 管理员关闭开关时，批改只使用 AI 规则指定模型的直接结构化路径。
2. 管理员开启开关时，两次普通批改后只调用一次指定结构化模型。
3. 切换系统默认模型不影响作业 `aiRule.modelType` 的实际路由。
4. 不支持结构化输出的 AI 规则模型在直接路径下有限失败，不产生无限循环。
5. 硬超时后 Celery 结果、AgentRun 和学生页面最终状态一致。
6. 现有教师人工批改、重新提交版本隔离和分差超过 10% 转人工行为保持不变。
